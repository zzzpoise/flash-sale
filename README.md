# flash-sale

基于 **Go + Gin + Redis** 的高并发秒杀系统，用 Lua 脚本保证库存扣减的原子性，用 Redis List 队列做异步削峰，后台 Worker 将订单异步落盘。

---

## 核心特性

| 特性 | 实现方式 |
| --- | --- |
| 库存不超卖 | Redis + Lua 脚本，`get / decrby` 原子执行，杜绝并发竞态 |
| 一人一单（防黄牛） | Redis Set 记录已购买用户，`sismember` 判重 |
| 异步削峰 | 抢购成功后仅写入 Redis List 队列，接口立即返回，不阻塞在数据库写 |
| 异步下单 | 后台 Worker 通过 `BRPOP` 阻塞消费队列，落盘生成订单 |
| 无外部 DB 依赖 | 订单以 JSON Lines 格式追加写入 `orders.jsonl` |
| 脚本内嵌 | `//go:embed` 将 Lua 脚本编译进二进制，部署无需附带文件 |

## 技术栈

- **语言**：Go 1.22
- **Web 框架**：Gin v1.9.1
- **缓存 / 队列**：Redis（go-redis v9）
- **原子操作**：Lua 脚本（`EVALSHA`，由 `redis.NewScript` 自动管理脚本缓存）

## 项目结构

```
flash-sale/
├── main.go            # 服务入口：Redis 初始化、秒杀接口、异步订单 Worker
├── stress.go          # 压测脚本（build tag: ignore，独立运行）
├── lua/
│   └── seckill.lua    # 秒杀核心 Lua 脚本：库存校验 + 扣减 + 用户判重
├── orders.jsonl       # 订单落盘文件（JSON Lines，一行一条）
├── go.mod
└── go.sum
```

## 快速开始

### 1. 准备环境

- Go 1.22+
- Redis 服务（默认连接 `localhost:6379`，无密码）

```bash
# Docker 一键启动 Redis
docker run -d --name redis -p 6379:6379 redis:7-alpine
```

### 2. 安装依赖

```bash
go mod download
```

### 3. 启动服务

```bash
go run main.go
```

启动成功后会看到：

```
✓ 成功连接 Redis
✓ 订单异步处理 Worker 已启动...
秒杀服务已启动在 :8080
```

> **注意**：每次启动都会把商品 `1001` 的库存重置为 **5**。想测试更多并发生效，修改 `main.go` 中 `rdb.Set(ctx, "seckill:stock:1001", 5, 0)` 的数值，或在启动前删除该 key。

## 接口说明

### `POST /seckill`

发起秒杀请求。

**Query 参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `user_id` | string | 否 | 用户标识，不传默认为 `anonymous` |

**请求示例**

```bash
curl -X POST "http://localhost:8080/seckill?user_id=user_1"
```

**响应消息**

| 返回消息 | 含义 |
| --- | --- |
| `秒杀成功！正在排队生成订单` | 抢购成功，已进入队列异步下单 |
| `手慢了，已被抢空` | 库存不足 |
| `您已经抢到过了，请勿重复下单！` | 该用户已购买过（防重复下单） |
| `商品不存在` | 库存 key 不存在 |
| `系统错误` | 脚本执行异常 |

```json
{ "message": "秒杀成功！正在排队生成订单" }
```

## 核心流程

```
              POST /seckill?user_id=xxx
                        │
                        ▼
            ┌───────────────────────┐
            │   Redis + Lua 原子脚本  │
            │ 1. 库存是否存在         │
            │ 2. 用户是否已购买       │
            │ 3. 库存是否充足         │
            │ 4. decrby + sadd       │
            └───────────┬───────────┘
             ┌──────────┼───────────┐
        返回 1        返回 0       返回 -2
        (成功)       (售罄)      (重复购买)
             │
             ▼
     LPUSH order:queue  ──► 立即响应客户端（削峰）
             │
             ▼
     Worker  BRPOP 消费
             │
             ▼
     append orders.jsonl（异步落库）
```

### Lua 脚本返回值约定

`lua/seckill.lua` 是整套并发安全的核心，脚本在 Redis 中单线程原子执行：

| 返回值 | 含义 |
| --- | --- |
| `1` | 扣减成功 |
| `0` | 库存不足 |
| `-1` | 库存 key 不存在 |
| `-2` | 用户重复购买 |

### Redis 数据结构

| Key | 类型 | 用途 |
| --- | --- | --- |
| `seckill:stock:1001` | String | 商品 1001 的剩余库存 |
| `seckill:users:1001` | Set | 已购商品 1001 的用户集合 |
| `order:queue` | List | 待处理订单消息队列 |

## 压测

`stress.go` 附带一个独立压测程序（文件头有 `//go:build ignore`，不会被编入主程序）。

**默认参数**：总请求 10000，并发协程 1000，用户 ID 在 `user_0 ~ user_1999` 间随机。

```bash
go run stress.go
```

**输出示例**

```
🚀 开始压测! 总请求: 10000, 并发数: 1000
====================================
✅ 压测完成！总耗时: 2.3s
📊 QPS (每秒处理请求数): 4347.82
📈 网络请求成功: 10000 次
📉 网络请求失败: 0 次
====================================
```

> 说明：这里的「成功」指 HTTP 状态码为 200。由于售罄、重复购买等业务失败同样返回 200，**业务层面的成功笔数应查看 `orders.jsonl` 的行数**——这正是验证「不超卖」的方式：库存为 5 时，压测后该文件应恰好新增 5 条订单。

**验证是否超卖**

```bash
wc -l orders.jsonl
```

## 设计取舍与可扩展方向

当前实现是一个精简可跑的秒杀内核，生产环境还可以继续补强：

- **库存预热**：改为在活动开始前批量加载库存，而非每次启动重置。
- **接口限流**：加令牌桶 / 滑动窗口，挡住无意义的重复刷单流量。
- **消费幂等**：多实例部署时保证消息重投不会产生重复订单。
- **真正落库**：将 `orders.jsonl` 替换为 MySQL，并在 `(user_id, product_id)` 上建唯一索引作为最终兜底。
- **队列可靠性**：`BRPOP` 消费失败即丢消息，可换用 Redis Stream + 消费组，或引入 Kafka / RocketMQ 支持 ACK 与重放。
- **订单状态机**：从「已支付」扩展为待支付 → 已支付 → 超时释放库存的完整链路。
- **可观测性**：接入 Prometheus 指标（QPS、库存余量、队列积压）与链路追踪。
